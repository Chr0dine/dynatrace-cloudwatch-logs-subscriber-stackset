# CloudWatch Logs → Dynatrace Subscriber

A CloudFormation stack that automatically subscribes CloudWatch log groups to the Dynatrace Firehose delivery stream when they are tagged for monitoring.

When someone applies the opt-in tag (for example `SendLogToDynatrace=true`) to a log group, CloudTrail records the call, an EventBridge rule picks it up, and a Lambda function running in your private VPC subnets subscribes **that log group**. A daily full check also reviews every tagged log group, catching any that were skipped earlier. Log groups are only subscribed if they also carry the required business tags (`BU:ApplicationName`, `BU:GEARID`, `BU:SoftwareInstallationId`), matched regardless of capitalization.

## Files

| File | Purpose |
| --- | --- |
| `cloudwatch-logs-dynatrace-subscriber.yaml` | The CloudFormation template. The Lambda code is inline in this file, and this is the copy that gets deployed. |
| `Final_CloudWatch_Logs_Subscriber_Lambda.py` | Standalone copy of the same Lambda code for reading, diffing and testing. Keep it in sync with the template (see [Updating the code](#updating-the-code)). |

## How it works

The function runs in one of two modes, chosen from how it was invoked.

**Targeted check** — triggered by tagging a log group:

```
Log group tagged TAG_KEY=TAG_VALUE
        │  (TagResource / TagLogGroup / CreateLogGroup)
        ▼
CloudTrail ──► EventBridge rule ──► Subscriber Lambda (private subnets)
                                        │
                                        ├─ 1. Read the current tags of the log group named in the event
                                        ├─ 2. Stop if it is no longer tagged TAG_KEY=TAG_VALUE
                                        ├─ 3. Stop if a required BU: tag is missing or blank
                                        ├─ 4. Find the Dynatrace Firehose stream and IAM role (cached)
                                        └─ 5. Create or update that log group's subscription filter
```

**Full check** — triggered by the daily schedule, or by running the function manually with `{}`:

```
Daily schedule / manual run ──► Subscriber Lambda
                                    │
                                    ├─ 1. List every log group tagged TAG_KEY=TAG_VALUE
                                    ├─ 2. Skip any missing a required BU: tag
                                    ├─ 3. Find the Dynatrace Firehose stream and IAM role (always fresh)
                                    └─ 4. Create or update the subscription filter on the rest
```

Bulk tagging 200 log groups therefore produces 200 short targeted runs, each touching one log group, rather than 200 runs that each check everything. Both modes are idempotent: log groups that are already correctly subscribed are left alone.

### Matching rules

| What | How it's matched |
| --- | --- |
| Firehose stream | Name contains `FIREHOSE_NAME_CONTAINS` **and** the region (e.g. `us-east-1`), case-insensitive. Exactly one stream must match, and it must be `ACTIVE`. |
| CloudWatch Logs role | Name contains `ROLE_NAME_CONTAINS` **and** the region, case-insensitive. Its trust policy must allow `logs.amazonaws.com`. Exactly one role must match. |
| Opt-in tag | `TAG_KEY` and `TAG_VALUE` are matched exactly (case-sensitive) by the EventBridge rule and by the function. In a targeted check the function re-reads the log group's tags, so a tag removed again before the run is respected. |
| Required tags | Each key in `REQUIRED_TAG_KEYS` must be present with a non-blank value. Key matching is case-insensitive, so `BU:GEARID`, `BU:gearid` and `bu:GearId` are all accepted. If a log group has several spellings of the same key, any one with a value satisfies it. |

### Results

Each run returns a summary with a `mode` field (`targeted` or `full`), counts per status, and a `details` entry per log group.

| Status | Meaning |
| --- | --- |
| `created` | A new subscription filter was added. |
| `updated` | The managed filter existed but pointed at the wrong stream, role or pattern, and was corrected. |
| `exists` | Already correct; nothing changed. |
| `missing_tags` | Skipped because one or more required tags are missing or blank. The log lists which ones. |
| `not_tagged` | Targeted check only: the log group no longer has the opt-in tag, or no longer exists. Nothing to do. |
| `skipped` | Skipped because the log group already has two other subscription filters (the CloudWatch Logs limit). |
| `error` | An AWS error occurred for this log group. Other log groups are still processed. |

The function returns status `200` when there are no errors and `207` when some log groups errored.

## Resources created

| Logical ID | Type | Purpose |
| --- | --- | --- |
| `SubscriberExecutionRole` | `AWS::IAM::Role` | Execution role for the Lambda (see [Permissions](#permissions)). The name is generated by CloudFormation, so the stack can be deployed in several regions without name clashes. |
| `SubscriberFunction` | `AWS::Lambda::Function` | The subscriber function. Python 3.13, runs in the selected VPC subnets, reserved concurrency of 1. |
| `CloudTrailTagRule` | `AWS::Events::Rule` | Starts a targeted check when the opt-in tag is applied to a log group. |
| `CloudTrailTagRulePermission` | `AWS::Lambda::Permission` | Allows that rule to invoke the function. |
| `FullCheckRule` | `AWS::Events::Rule` | Starts the daily full check. Not created if the schedule parameter is empty. |
| `FullCheckRulePermission` | `AWS::Lambda::Permission` | Allows the schedule to invoke the function. Not created if the schedule parameter is empty. |

The template also has two **Rules** that run when you submit the stack, before anything is created: every selected subnet and every selected security group must belong to the selected VPC.

**Outputs:** `FunctionName`, `FunctionArn`, `ExecutionRoleArn`, `CloudTrailTagRuleArn`, and `FullCheckRuleArn` (when the schedule is enabled).

## Parameters

### Function

| Parameter | Default | Notes |
| --- | --- | --- |
| Function name | `CloudWatch-Logs-Dynatrace-Subscriber` | Must be unique within the region. |
| Memory (MB) | `256` | 128 to 10240. |
| Timeout (seconds) | `300` | 3 to 900. Size this for the full check, which visits every tagged log group; targeted checks take seconds. |

### VPC

Laid out in the same order as the Lambda console's VPC settings.

| Parameter | Default | Notes |
| --- | --- | --- |
| VPC | none | Dropdown of VPCs in the account and region. |
| Allow IPv6 traffic for dual-stack subnets | `false` | Set to `true` only if the subnets are dual-stack. |
| Subnets | none | **Private subnets only**, ideally two or more in different Availability Zones. They need a route to a NAT gateway. |
| Security groups | none | Must allow outbound HTTPS (443). |

### Environment variables

| Parameter | Default | Notes |
| --- | --- | --- |
| `TAG_KEY` | none (required) | Opt-in tag key. Case-sensitive. |
| `TAG_VALUE` | `true` | Opt-in tag value. Case-sensitive. |
| `REQUIRED_TAG_KEYS` | `BU:ApplicationName,BU:GEARID,BU:SoftwareInstallationId` | Comma-separated. Case-insensitive keys, values must be non-blank. Leave empty to disable the check. |
| `FIREHOSE_NAME_CONTAINS` | none (required) | Text in the Dynatrace Firehose stream name. |
| `ROLE_NAME_CONTAINS` | none (required) | Text in the CloudWatch Logs → Firehose role name. Also scopes the function's `iam:PassRole` permission, which **is** case-sensitive, so enter it with the role name's exact capitalization. |
| `SUBSCRIPTION_FILTER_NAME` | `DynatraceManagedSubscription` | Name of the filter the function manages. |
| `FILTER_PATTERN` | empty | CloudWatch Logs filter pattern. Empty forwards all log events to Dynatrace. |
| `LOG_LEVEL` | `INFO` | Minimum level written to the function's own log (see [Logging](#logging)). Does not affect what is sent to Dynatrace. |

### Daily full check

| Parameter | Default | Notes |
| --- | --- | --- |
| Schedule (UTC) | `cron(0 6 * * ? *)` | EventBridge schedule expression; the default runs daily at 06:00 UTC. Any `cron(...)` or `rate(...)` expression works. Leave empty to disable the full check. |

## Permissions

The execution role has the AWS managed policy `AWSLambdaExecute` plus one inline policy:

| Statement | Actions | Why |
| --- | --- | --- |
| `CloudWatchLogsDiscovery` | `logs:DescribeLogGroups`, `logs:DescribeSubscriptionFilters`, `logs:PutSubscriptionFilter`, `logs:ListTagsForResource` | Read a log group's tags (targeted check) and manage its subscription filters. |
| `FirehoseDiscovery` | `firehose:ListDeliveryStreams`, `firehose:DescribeDeliveryStream` | Find the Dynatrace stream. |
| `RoleDiscovery` | `iam:ListRoles` | Find the CloudWatch Logs role. |
| `PassLogsRole` | `iam:PassRole` on `role/*<ROLE_NAME_CONTAINS>*` in this account | Hand that role to CloudWatch Logs when creating a subscription. |
| `ec2permissions` | `ec2:CreateNetworkInterface`, `ec2:DescribeNetworkInterfaces`, `ec2:DeleteNetworkInterface`, `ec2:DescribeSubnets`, `ec2:AssignPrivateIpAddresses`, `ec2:UnassignPrivateIpAddresses` | Required for a Lambda that runs in a VPC. |
| `FindResourcesByTag` | `tag:GetResources` | Find every tagged log group (full check). |

`AWSLambdaExecute` is broad: it allows all CloudWatch Logs actions and reading and writing objects in any S3 bucket expect a security review to ask about it.

## Prerequisites

- **CloudTrail:** A trail (an organization trail should count) recording write management events in the target region. Without it, tagging doesn't trigger the function; only the daily full check would subscribe log groups.
- **Network:** Private subnets with a NAT gateway route, and security groups allowing outbound 443. The function calls the CloudWatch Logs, Firehose, IAM and Resource Groups Tagging APIs.
- **Firehose and role:** Exactly one matching Firehose stream and exactly one matching CloudWatch Logs role per region (see [Matching rules](#matching-rules)).
- **Function name:** No existing Lambda with the same name in the region. If an older version of this function has triggers attached, remove them so two copies don't run.
- **Concurrency:** Reserving 1 execution requires the account to keep at least 100 unreserved. The standard 1,000 limit is fine; new low-limit accounts are not.
- **Deploy permissions:** Permission to create IAM roles, Lambda functions and EventBridge rules, and to acknowledge `CAPABILITY_IAM`.

## Deployment

The stack is regional. Deploy it once in each region that has a Dynatrace Firehose stream (CloudFormation StackSets can do this in one step).

### Console

1. CloudFormation → **Create stack** → **With new resources (standard)** → **Upload a template file**, and choose `cloudwatch-logs-dynatrace-subscriber.yaml`.
2. Enter a stack name and fill in the parameters.
3. Accept the default stack options.
4. On the review page, tick **I acknowledge that AWS CloudFormation might create IAM resources** and submit.

### CLI

```bash
aws cloudformation deploy \
  --template-file cloudwatch-logs-dynatrace-subscriber.yaml \
  --stack-name cwlogs-dynatrace-subscriber \
  --capabilities CAPABILITY_IAM \
  --region us-east-1 \
  --parameter-overrides \
    VpcId=vpc-xxxx \
    SubnetIds=subnet-aaaa,subnet-bbbb \
    SecurityGroupIds=sg-xxxx \
    TagKey=SendLogToDynatrace \
    FirehoseNameContains=<text> \
    RoleNameContains=<ExactCaseText>
```

The template is just under the 51,200-byte limit for sending a template directly. If future edits push it over, add `--s3-bucket <bucket>` to the command so the CLI uploads it through S3. Console uploads are unaffected.

## After deploying

1. **Backfill.** Log groups that were tagged before the stack existed are picked up by the first daily full check. To do it immediately, run the function from the Lambda console's **Test** tab with `{}` as the event; the response should show `"mode": "full"` and the counts.
2. **Test the trigger.** On a test log group that has all three BU tags, apply the opt-in tag the way your teams normally do, for example:

   ```bash
   aws logs tag-resource \
     --resource-arn arn:aws:logs:REGION:ACCOUNT:log-group:NAME \
     --tags SendLogToDynatrace=true
   ```

   Within a few minutes, `/aws/lambda/<FunctionName>` should show `Targeted check: only processing ['NAME']` followed by `Created subscription on NAME`, and the log group's **Subscription filters** tab should list the filter.
3. **Test the tag check.** Repeat with a log group missing one BU tag. The function should log a warning naming the missing tag.

## Operations

### Logging

The function logs to `/aws/lambda/<FunctionName>`. `LOG_LEVEL` is a minimum threshold:

| Setting | Writes |
| --- | --- |
| `DEBUG` | Everything, including request-level logging from the AWS SDK (very verbose). |
| `INFO` | Each log group processed, plus warnings and errors. |
| `WARNING` | Skipped log groups and errors. |
| `ERROR` | Errors only. |

### Lookup caching

Finding the Firehose stream and IAM role means listing every delivery stream and every IAM role in the account, which is the slowest part of a run. Targeted checks cache both results for 15 minutes on the warm Lambda instance; with reserved concurrency of 1, queued runs from bulk tagging all share that instance. Full checks always look both up fresh and refresh the cache, and any run that ends with an error clears it.

### Monitoring

If a run fails outright (for example, the Firehose stream can't be found), Lambda retries it twice and then drops the event. Per-log-group errors don't trigger a retry; they show up as `error` entries in that run's results. A CloudWatch alarm on the function's **Errors** metric is the simplest way to be told about outright failures. A log group whose targeted run was dropped is still picked up by the next daily full check.

### Updating parameters

Update the stack with new parameter values. Changing `TAG_KEY` or `TAG_VALUE` updates the function and both EventBridge rules.

### Updating the code

The code that runs is the inline copy in the template's `SubscriberFunction` → `Code` → `ZipFile` block. To change it, edit that block (and mirror the change in the `.py` file), then update the stack. Edits made directly in the Lambda console are overwritten on the next stack update.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Tagging a log group doesn't invoke the function | No CloudTrail trail in the region; tag key or value capitalization doesn't match exactly; log group tagged through Tag Editor / Resource Groups Tagging API (recorded as a different CloudTrail event) | Confirm the trail; check the exact tag; check the rule's **Invocations** metric in EventBridge. The daily full check will still subscribe the log group. |
| Runs time out | A selected subnet has no NAT route (for example, a public subnet), or the security group blocks outbound 443 | Fix the routes or security group, or update the stack with different subnets. |
| Some runs succeed and others time out | Mix of working and non-working subnets | Same as above; Lambda spreads runs across all selected subnets. |
| Full check times out | Too many tagged log groups for the timeout | Raise the Timeout parameter (up to 900 seconds). |
| `No Firehose delivery stream was found` / `Multiple Firehose delivery streams matched` | `FIREHOSE_NAME_CONTAINS` too narrow or too broad, or the region isn't in the stream name | Adjust the parameter. |
| `No CloudWatch Logs subscription role was found` / `Multiple ... roles matched` | `ROLE_NAME_CONTAINS` too narrow or too broad, region missing from the name, or the role doesn't trust `logs.amazonaws.com` | Adjust the parameter or the role's trust policy. |
| `AccessDenied` on `iam:PassRole` | `ROLE_NAME_CONTAINS` capitalization differs from the actual role name | Re-enter it with the exact capitalization. |
| Log group reported as `missing_tags` | One or more BU tags missing or blank | Add the tags. The next daily full check subscribes it, or run the function manually with `{}`. |
| Log group reported as `not_tagged` | The opt-in tag was removed (or the log group deleted) before the run | Nothing to do, unless the tag removal was unintended. |
| Log group reported as `skipped` | It already has two other subscription filters | Remove one, or leave it out of Dynatrace. |
| `Could not find a log group in the CloudTrail event` warning | Unexpected event shape | The function falls back to a full check automatically. |
| Stack fails on `ReservedConcurrentExecutions` | Account concurrency limit too low | Request a limit increase. |
| Stack fails on submit with a subnet or security group message | A selection isn't in the chosen VPC | Pick resources from the selected VPC. |

## Limitations

- **Late BU tags wait for the daily check.** Fixing a skipped log group's BU tags doesn't trigger a run; the next full check picks it up. Run the function with `{}` to do it sooner.
- **Nothing is unsubscribed automatically.** Removing the opt-in tag, or deleting the stack, leaves existing subscription filters in place.
- **Tagging method matters for the instant trigger.** The rule matches CloudWatch Logs' own tagging calls (`TagResource`, `TagLogGroup`, and `CreateLogGroup` with tags). Other tagging methods rely on the daily full check; test each method your teams use.
- **Firehose or role changes can take up to 15 minutes** to reach targeted checks because of the lookup cache. The next full check, or any failed run, refreshes it immediately.
- **Public subnets aren't blocked.** Nothing stops a public subnet from being selected; it just won't work.
- **Runs are serialized.** Reserved concurrency of 1 means bulk tagging queues runs; each is short, so a few hundred clear in minutes.
- **Stack deletion can be slow** while Lambda releases its VPC network interfaces.
